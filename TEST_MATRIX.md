# Test matrix

"Verified" means a ROM was actually loaded and played through RetroBox on the stated target. Nothing here has been run on the Xiaomi Mi TV 4A or with a Cosmic Byte Stratos Xenon yet. **For SNES, Game Boy, Game Boy Color and GBA the ROMs were original test programs generated by this repo (`tools/`), not commercial games** — no user-supplied SNES/GB/GBA ROMs were available, so real-game compatibility of those cores is untested.

First run on the real TV (2026-10-17, Xiaomi MiTV-AXSO0, Android 9, armeabi-v7a, ~1 GB RAM): the debug build installs and starts, and a Bluetooth Sony-style pad ("Wireless Controller" 054c:09cc) drives one NES game. A TV-only bug (the TV's `virtual-search` device was counted as Player 1's gamepad) was found and fixed. Speed, graphics looks, SNES/GB/GBA, the device tests and the Cosmic Byte pad are still NOT tested on the TV.

**Genesis was removed on 2026-10-17** (cores, tests and test ROM deleted); the dated sections below that mention it are history.

Target used so far: Android TV emulator `sdk_google_atv64_arm64` (Android 16 / API 36, 1920x1080, Apple-silicon host, GLES 3.0 translator). Emulator numbers say nothing about real-TV speed.

## Manual verification log (Android TV emulator, 2026-10-17)

Exercised by hand/ADB key events (the emulator is shared, other activity on it is not mine):

* Debug and R8-minified release APKs install and launch from the leanback launcher; the release build was signed with a throwaway key and played the test ROM.
* Home → NES card → ROM picker → game; D-pad/OK navigation; Back in game opens the pause menu; Back inside the menu goes up one level / resumes.
* Pause menu items run: Save state (slot picker, 4 slots), overwrite confirmation, Load state (game resumed from the saved moment), Quit with confirmation (returns to the ROM list).
* **Not exercised yet:** Reset, Screen-mode cycle, Filter toggle, Audio mute, "Yes, quit" error paths on a real unsupported ROM on-device (covered only by unit tests).
* Held keys reach the game: Start advanced a commercial game's title menu; A (OK on the remote) turned the test ROM's background red only while held.
* Home key during play pauses emulation (emulation thread at 0% CPU) and keeps the process; the app can be resumed.
* An unclean exit (force-stop/reinstall during play) leaves `session.lock`, and the next start logs "Previous session ended unexpectedly" to the error log.
* Audio: AudioTrack opened at the core's 48 kHz, 0 underruns, 0 dropped frames reported in the pause-menu info line. In an earlier run this emulator's audio sink stopped draining and the first version froze the game; audio writes now time out and drop samples instead (that code path was fixed but only observed once). **Sound was never heard by a human.**
* Frame pacing in the emulator: 59.7–60.9 fps measured, `retro_run` avg ≈0.5–0.6 ms, occasional spikes up to ~31 ms (cold-start/GC; not analysed). These numbers come from an Apple-silicon host and say nothing about the Mi TV.

### Clean display titles (2026-10-17, emulator)

Titles shown in the app are cleaned from the file name (display only; the file, its saves and its picture keep the real name): `_` `-` `+` become spaces, (region) / [dump] tags and other symbols are removed, "Legend of Zelda, The" becomes "The Legend of Zelda", all-lower or ALL-CAPS names are re-cased (small words like "of" stay lower, roman numerals like "II" stay upper, a lone "n" becomes 'n', well-known acronyms such as FIFA/NBA stay upper) and mixed-case words such as "FireRed" are left alone. Unit-tested (`DisplayTitleTest`, 9 cases). Seen on the emulator with temporary copies of my test ROM: `SUPER_MARIO-BROS_(U)_[!].nes` → "Super Mario Bros", `legend-of-zelda,-the.nes` → "The Legend of Zelda", `chip-n-dale-2.nes` → "Chip 'n' Dale 2", `sonic.smc` → "Sonic". Apostrophes that the file name lacks cannot be restored ("KIRBYS_ADVENTURE" → "Kirbys Adventure"), and an all-caps acronym not on the built-in list gets re-cased (e.g. "NBA" is kept, "TMNT" is kept, an unknown "XYZ" becomes "Xyz").

### Milestone 4 manual log (same emulator, 2026-10-17)

Driven with `adb shell input keyevent` and screenshots of the emulator screen (test ROMs only; screenshots are not committed).

* SNES / GB / GBC / GBA test ROMs start from Home → system card → ROM list → OK; the frame size, core name, audio rate and underrun counters in the pause-menu info line match the table above (SNES `512x448 @ 32040 Hz`, GB `160x144 @ 32768 Hz`, 0 underruns / 0 dropped on all).
* Every mapped button was confirmed by a colour change in the test ROM (SNES A/B/X/Y/L/R, GBA A/B/L/R/Select, GB/GBC A/B); buttons a system lacks (X/Y on GB/GBA) left the picture unchanged.
* Save state → change game → load state restored the earlier frame on SNES, GB, gpSP and mGBA; the overwrite confirmation appeared when saving over a slot that held another core's state.
* Cartridge saves: counter written to SRAM, autosave (≤20 s) or quit wrote `saves/sram/<system>/<rom>.srm`, relaunch showed the same counter. Because of the "baseline" change (below) a GBA game that never writes its save no longer leaves a 128 KiB file behind (not separately tested with a save-less GBA ROM; covered by the code path only).
* A zero-filled 40 KB `.gba` was rejected with "not a valid GBA ROM (bad header)" before reaching a core.
* The mGBA ↔ gpSP switch (ROM list, first card) works. Loading a slot saved by the *other* core is refused by existing Milestone-3 code (`coreId` check) but I did not trigger that on the device.

**Bugs found and fixed while doing this** (all invisible to unit tests):

1. *Game Boy picture ~10x too dark.* `cores/mk/gambatte/Android.mk` did not define `-DVIDEO_RGB565` like upstream's Makefile.libretro, so gambatte ran its 32-bit path, whose output was not scaled. Fixed in the overlay; gambatte now delivers RGB565 (less memory bandwidth, relevant for the Mali-450).
2. *Short key taps were lost.* `adb input keyevent` (and a quick remote tap on a slow frame) presses and releases within milliseconds, i.e. between two `retro_run` calls, so the core never saw them. The host now latches every press until one frame has seen it.
3. *Baseline for cartridge saves.* The first version compared SRAM with "nothing saved yet", so cores that always expose battery RAM (gpSP: 128 KiB of 0xFF) wrote a junk `.srm` on first autosave. The baseline is now the core's own state after loading.

**Not verified / known gaps for these four systems**

* **Real games.** No commercial SNES/GB/GBA ROM was available; compatibility is only what the cores' authors claim. snes9x2005 has no SuperFX/SA-1-class coprocessor support; GBA games needing a particular save type rely on the cores' ROM-string detection (our test ROM carries the `SRAM_V113` marker).
* **armeabi-v7a.** The emulator is arm64-only, so none of the 32-bit core builds (the likely TV ABI) has ever executed, and gpSP's ARM dynarec — the reason it is the TV default — was not exercised.
* **Audio was never heard** (the emulator's output is not audible to me): only the AudioTrack opens at the core's rate, with 0 underruns. The SNES test ROM does not program the SPC700, so SNES audio was silence by construction; GB/GBC/GBA test ROMs play a tone on A.
* **Real controller / real keyboard.** The RetroArch-style keyboard defaults (Z X A S Q W Enter Right-Shift) are covered by unit tests only; the emulator's console-injected key events never reached the app, so they were not tried on a device.
* **Game Boy real-time clock** (e.g. Pokémon Gold/Silver) and Super Game Boy borders are not handled; RTC data is not persisted.
* **mGBA** reports a 65536 Hz audio rate; Android resamples it, it was not measured for CPU cost on a TV.
* Cartridge saves are keyed by system + ROM name, not by core; the gpSP↔mGBA round trip worked for SRAM, but EEPROM/Flash saves were not tried.
* Real-TV frame rates for any of these cores: unknown.

How: the emulator has `/system/bin/uinput`, so I registered two virtual gamepads (`RB Test Pad 1/2`, Android device ids 6 and 7: `KEYBOARD | GAMEPAD | JOYSTICK`, buttons + a hat axis) and injected events into them; the NES test ROM (`tools/make_test_rom.py`, now also reads port 2 and moves a second, blue square) shows who moved. These are *virtual* pads on one emulator, not real controllers.
* **Routing**: with both pads present at game start the log reads `2-player game: pads [RB Test Pad 1, RB Test Pad 2]`. Pad 1's hat right moved only the orange (Player 1) square (+330 px, y unchanged); pad 2's hat up moved only the blue (Player 2) square (−290 px, x unchanged), both at the same time.
* **Custom Player 2 controls**: with `player2` → `system:nes` → `UP = Pad A` in `profiles.json`, pad 2's A button moved the blue square up; pad 1's A (default mapping = RetroPad B) moved nothing. The keyboard-source events from `adb input` still drive Player 1.

**Preset timings** (in-app timer with the overlay on, `adb logcat -s RetroBoxPerf`, Game Boy test ROM 160x144, 1080p output, emulator on an Apple-silicon host through the GLES-translator, 4 one-second windows each):

| Preset (look) | fps | draw avg (incl. glFinish) | draw max |
|---|---|---|---|
| Plain (off, nearest) | 59.6–59.7 | 0.96–2.21 ms | 1.6–4.2 ms |
| Smooth pixels (sharp bilinear) | 59.4–60.0 | 0.97–1.81 ms | 2.6–4.3 ms |
| CRT | 59.6–59.9 | 0.97–2.10 ms | 1.7–3.9 ms |
| Handheld LCD (grid, integer ×6) | 59.5–59.8 | 1.06–1.55 ms | 2.8–3.5 ms |

All four were indistinguishable here (noise ±1 ms, core rate 59.73 fps), so **this emulator tells us nothing about cost on a Mali-450**: its GPU is the host's, not a 2012 tile-based part with ~1/50th of the fill rate. No claim is made that any preset is cheap or expensive on the TV. The doc text says presets describe a *look*; "Plain" is only called "the cheapest path" because it runs the fewest shader instructions.

Not verified / known limits:
* **No Mali-450 run at all.** Fragment shaders there are `mediump`-only; `fract(uv * texSize)` (scanlines, CRT, LCD grid) may band or shimmer at fp16 precision. The Performance screen reports `fragment highp: yes/no` for the game's own GL context so this can be checked on the TV first.
* CRT shader cost at 1366x768 / 1080p on that GPU, and whether a 1 GB TV holds the extra programs (they are only built when used).
* The OS font/overscan of the real TV: the safe-area default is 0 % and the user must find their own value; there is no test pattern.
* Safe area is applied to Compose screens by padding; scrolled content is clipped at the margin rather than at the screen edge.
* Audio is not audible-verified (see above). The 30 ms fade is untested by ear.
* Per-system choices stored by Milestone 3–5 builds (`SharedPreferences "graphics"`) are ignored, not migrated.
* Overlay timing uses `glFinish`, which on a tile-based GPU can serialise work and make the *game* slower while it is shown.
